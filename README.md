# isutori

ISUCON で、チームの共有サーバーへのデプロイとベンチ実行を 1 回ずつ順番に回すためのツールです。

デプロイやベンチなど、各ステップで実行するコマンド (フック) は、チームが競技リポジトリに用意します。isutori は順番待ちの列 (キュー) を管理し、順番が来たらフックを順に実行します。キューは `queue.host` (通常 s1) に置き、SSH で操作するので、サーバーに常駐プロセスは要りません。

## エージェントで導入する

Claude Code か Codex を使っているなら、plugin を入れて `setup-isutori` を実行すれば、導入はエージェントに任せられます。既存のデプロイ手段や集計スクリプトを isutori から呼べるようにするところから、最初のベンチで確かめるところまで、エージェントが必要なことを尋ねながら進めます。

```sh
# Claude Code
claude plugin install isutori --marketplace traP-jp/isutori
# 競技リポジトリで /isutori:setup-isutori <ポータルの URL> を実行する

# Codex
codex plugin marketplace add traP-jp/isutori
codex plugin add isutori@isutori
# 競技リポジトリで $ から isutori:setup-isutori を選び、ポータルの URL を添えて実行する
```

以降の章は、手動で導入するときと、導入した後の動きを知りたいときのための説明です。

## 手動で導入する

次の環境を前提にしています。

- 競技リポジトリを Git で管理していて、origin へ push できる
- 手元から各サーバーへ、`ssh s1` のように SSH の別名で入れる
- 手元に mise と Go がある (mise の `go:` バックエンドは Go でビルドする)
- 手元が Linux、macOS、WSL のどれか (Windows で直接は動かない)

チーム全員が同じバージョンを使うよう、競技リポジトリの直下で mise にバージョンを固定して入れ、雛形を作ります。

```sh
mise use --pin go:github.com/traP-jp/isutori@latest
isutori init                # isutori.toml の雛形を書き、.gitignore に .isutori/ を足す
```

次に、`isutori.toml` の `[hooks]` を埋めます。埋めたら、フックのスクリプトと一緒に commit し、`ops.ref` のブランチ (既定は main) へ push します。isutori はフックと `isutori.toml` を origin から取り出して使うので、push する前の内容は使われません。

```sh
isutori bench               # HEAD をデプロイしてベンチを回す
isutori status --json
```

| コマンド | 内容 |
|---|---|
| `bench [--ref REF] [--mode measure\|final] [--requester NAME]` | REF をデプロイしてベンチを回す |
| `publish RUN_DIR` | 保存済みの回の publish フックだけを再実行する |
| `guard` | 自分の実行がキューの先頭でなければ 0 以外で終了する |
| `receive [--listen ADDR]` | `bench` のフックから呼び、手動で入力された結果を受け取る |
| `autobench [OPTIONS] PORTAL_URL TARGET` | `bench` のフックから呼び、ユーザースクリプトにベンチを回させる |
| `inspect [--listen ADDR] [--userscript FILE] PORTAL_URL` | 描画後の DOM と操作履歴を手元に記録する |
| `status [--json]` | キューの中身と、最後にデプロイされたものを表示する |
| `queue clear` | キューを空にする。キューが詰まったときの強制解除用 |
| `init` | `isutori.toml` の雛形を書く |
| `docs` | この README を表示する |
| `help` | コマンドの一覧と使い方を表示する |
| `userscript [MATCH_PATTERN...]` | ユーザースクリプトを書き出す |
| `mock-portal` | 偽ポータルを起動する |

`bench` の REF は既定で `HEAD` です。サーバーが取りに行けるよう、先に origin へ push しておきます。`guard` は、デプロイ手段の冒頭で呼びます。

`bench --mode final` は、競技の終わりに最終計測へ向けた状態をデプロイするときに使います。フックには `ISUTORI_MODE=final` が渡るので、デプロイ手段の中でログの出力やプロファイラを止めてください。ふだんの測定は、既定の `measure` で回します。

`bench` は進行状況を stderr に、実行結果をまとめた JSON を stdout に出します。終了コードは、ベンチが pass なら 0、途中でエラーなら 1、ベンチが fail なら 2 です。エージェントに使わせるときは、バックグラウンドで起動して待ち時間に別の作業をさせてください。

順番を待つ間、isutori は 3 秒ごとに `queue.host` へ SSH で接続します。ベンチ中のサーバーの負荷を増やさないよう、`~/.ssh/config` で接続を使い回す設定にしておくことを勧めます。

```
Host s1
  ControlMaster auto
  ControlPath ~/.ssh/cm-%C
  ControlPersist 60
```

### 計測するコミットと並行実行

複数の worktree から同時に `bench` を実行できます。isutori は origin のブランチとタグを実行ごとに分けて取得し、通常の `origin/*`、ローカルのタグ、`FETCH_HEAD` は更新しません。通常の fetch とも取得先が重ならないため、isutori のために手作業の fetch を止める必要はありません。

`HEAD`、ローカルのブランチとタグ、コミット ID は手元の内容を使います。`origin/main`、`refs/remotes/origin/main`、`origin/main~1` は今回取得した内容から解決します。`HEAD@{upstream}` などが origin のブランチを指す場合も同じです。手元にないタグは今回取得したタグを使います。アプリのコミットが origin のいずれかのブランチに含まれなければ、キューへ登録せず停止します。

`origin/main` などの短い参照名がローカルブランチやタグと重なる場合は、曖昧な指定として停止します。ローカルブランチは `refs/heads/origin/main`、origin のブランチは `refs/remotes/origin/main` のように指定してください。

`--ref` と `ops.ref` に `FETCH_HEAD` や origin の過去の reflog (`origin/main@{1}` など) は指定できません。取得時点のブランチ名かコミット ID を指定してください。アプリと運用コードのコミットはキュー登録前に確定し、待機中にブランチが進んでも変更しません。

取得に使った `refs/isutori/<実行 ID>/` の参照は実行終了時に削除します。強制終了や電源断では残る場合がありますが、次の実行は別の参照を使います。isutori は共有の参照を prune しないため、不要になったリモート追跡参照の整理は通常の Git 操作で行ってください。

## 測定の流れ

`isutori bench` を 1 回実行するごとに、キューに 1 枚のチケットを並べます。先頭のチケットを持つ実行だけが、共有サーバーを操作できます。

1. REF が origin にあるか確かめ、`ops.ref` (既定 `origin/main`) を取り出す。`isutori.toml` とフックは、取り出したものを使う
2. チケットをキューに並べ、先頭になるまで待つ
3. `deploy` → `health` → `prepare` → `bench` → `collect` → `analyze` → `publish` の順に進む
4. `cleanup` を呼ぶ。`deploy` に進んだ実行では、途中で失敗したときや Ctrl-C で中断したときにも呼ぶ

チケットにはリース (有効期限) があり、isutori は実行中ずっとリースを延長します。最後の延長から `lease_ttl` (既定 120 秒) が過ぎたチケットは、持ち主の isutori が止まったものとみなして、待っている側が消します。リースが切れていた実行は、サーバーが次の人に渡っている可能性があるため `cleanup` を呼びません。リースの延長が `lease_ttl` の 4 分の 3 の時間続けて失敗した実行も、リースが切れたものとみなして止めます。

Ctrl-C をもう一度押すと、実行中のフックを止め、`cleanup` を飛ばしてキューを空けてから終了します。3 回目を押すと、何も待たずに終了します。

`status` が表示するデプロイの記録には `state` があります。`deploy` を始めるときに `deploying` として書き、`health` が通ると `healthy` に書き換えます。`health` が未設定なら、`healthy` ではなく `deployed` にします。

## フックの書き方

フックは `isutori.toml` の `[hooks]` に書きます。`deploy` と `bench` は必須で、ほかのフックは未設定なら飛ばします。

isutori は、`ops.ref` から取り出したディレクトリを作業ディレクトリにして、フックを `sh -c` で実行します。フックの中では `isutori guard` をそのまま呼べます。

フックが 0 以外で終了するか、上限の時間を超えると、残りを飛ばして `cleanup` へ進みます。ただし、`collect` や `analyze` が失敗した場合は、取得済みのベンチ結果を共有できるよう `publish` を試してから進みます。中断やリース切れの場合は `publish` を試しません。上限は `hooks.timeout` (既定 10 分) です。`bench` だけは、ポータルの順番待ちを含むため `hooks.bench_timeout` (既定 20 分) で別に決めます。

キューへ並ぶ前に行いたい処理は、競技リポジトリ側で `isutori bench` を呼ぶコマンドに組み込めます。例えば、チームの掲示板から新着情報を取得し、作業範囲や計測の前提を確認する用途が考えられます。

`hooks.bench` は順番待ちとデプロイの後に実行されるため、計測するかを判断するための情報確認は呼び出し元で行ってください。情報を表示しても、読んで判断したことにはなりません。バックグラウンドで実行する場合は、出力された情報を確認する手順も用意してください。

フックには次の環境変数を渡します。

| 変数 | 内容 |
|---|---|
| `ISUTORI_RUN_ID` / `ISUTORI_RUN_DIR` | この実行の ID と作業ディレクトリ |
| `ISUTORI_APP_COMMIT` | デプロイするアプリのコミット |
| `ISUTORI_OPS_COMMIT` | フックを取り出したコミット |
| `ISUTORI_MODE` | `measure` か `final` |
| `ISUTORI_REQUESTER` / `ISUTORI_TICKET_ID` | 実行した人とチケット |
| `ISUTORI_REPO` | 手元の競技リポジトリのルート |
| `ISUTORI_CONFIG` | 使っている `isutori.toml` |
| `ISUTORI_BENCH_RESULT` | `bench` のフックが結果を書くファイル |

`$ISUTORI_RUN_DIR` には次のファイルができます。

- `run.json`: チケット、対象コミット、ベンチ結果、各ステップの状態と所要時間。実行の情報はキュー登録前に保存し、各ステップの開始前と終了後に更新します
- `bench.json`: `bench` のフックが書いたベンチ結果
- `run.log`: isutori とフックの出力

`run.json` は isutori が管理します。フックから書き換えず、成果物は別のファイルに保存してください。

## publish フックの約束事

publish は取得済みのベンチ結果と、その時点で手元にある成果物を共有するフックです。通常の実行でも、共有だけの再試行でも、次の条件を満たすように書いてください。

- `run.json` を共有し、実行 ID、アプリと運用コードのコミット、ベンチの合否・スコア・メッセージ、各ステップの状態を残す。
- `collect` や `analyze` が失敗しても動くようにする。ログや分析結果が無くてもベンチ結果を共有し、途中までの成果物を完全な計測として扱わない。
- 同じ実行 ID への再送は既存の記録を更新するか、変更がなければ成功として扱う。前の送信が成功してから応答だけを受け取れなかった場合にも、記録を重複させない。
- 共有先から成功を確認してから終了コード 0 を返す。コピーや送信をバックグラウンドで始めただけで成功にしない。
- 競技サーバーを操作せず、手元の成果物だけを共有する。publish はキュー外でも再実行されるので、`isutori guard` を使う処理を含めない。
- 共有に使う clone などを複数の回が使う場合は、フック側で競合を防ぐ。同じ回の重複実行は isutori が防ぐが、別の回や別のマシンからの送信は保存先に応じて調停する。

保存先や送信方法は競技リポジトリ側で選びます。共有先が使えない間も、手元の実行ディレクトリは残ります。共有フックの導入時には、成果物が無い回、途中までの回、送信に失敗した回の再試行、成功した回の再送を確認してください。

## 保存済みのベンチ結果を共有し直す

`collect`、`analyze`、`publish` が失敗した後や、プロセスが止まった後は、元の実行ディレクトリを指定して共有だけを再試行できます。

```sh
isutori publish .isutori/runs/<run_id>
```

再試行する前に、その回の `ops/` に保存された publish フックが、[publish フックの約束事](#publish-フックの約束事)を満たすことを確かめてください。現在のブランチでフックを修正しても、保存済みのフックには反映されません。再試行には保存済みの設定とフックを使い、実行 ID、対象コミット、モードを引き継ぎます。

`bench.json` を検証して `run.json` に反映するので、結果を保存した後、bench ステップの終了を記録する前に止まった回にも使えます。既に `run.json` にあるベンチ結果と食い違う場合は停止します。元の実行や別の再試行が動いている間も停止します。ロックのファイルを削除せず、実行中のプロセスが終わるのを待ってください。

このコマンドはキューに並ばず、publish フックだけを実行します。デプロイ、ベンチ、回収、分析、cleanup は再実行しません。`ISUTORI_TICKET_ID` は空になります。外部への書き込みは、通常の共有と同じ承認のもとで行ってください。

publish と手元の記録の保存が成功すれば終了コード 0、失敗すれば 1 を返し、stdout に実行記録の JSON を出します。元の実行の `error` とステップの履歴は消さず、再試行した publish を追記します。ベンチが fail でも、共有に成功した場合の終了コードは 0 です。

必要なのは、元の場所にある実行ディレクトリと、正常な `run.json`、`bench.json`、保存済みの `ops/` です。結果の保存前に止まった回や、これらのファイルを失った回は回復できません。ポータルからの結果の再取得、ログの再回収、手元以外への自動バックアップは行いません。

### 記録から状態を判断する

`bench.passed` はベンチ自体の合否です。たとえば collect が失敗し、その後の publish が成功した回では、ベンチの pass を保持したまま実行全体はエラーになります。`isutori bench` の終了コードは 1 です。共有だけの再試行の終了コードとは区別してください。

`stages` の各要素には、`name`、`status`、所要時間の `seconds`、失敗した場合の `error` が入ります。

| status | 意味 |
|---|---|
| `running` | 開始を記録したが、終了はまだ記録していない |
| `succeeded` | 処理が成功した |
| `failed` | 処理が失敗した。error に理由がある |
| `skipped` | フックが未設定なので実行していない |
| `unknown` | 再試行時に、前の処理の終了記録が無かった |

失敗のために到達しなかったステップは記録しません。同じ名前のステップが複数あれば、最後のものが最新の試行です。再試行前の `running` は、成功か失敗かを断定せず `unknown` にします。古い版の記録には status がありません。その場合は、ステップの有無と error を確認します。

手元の `run.json` は publish の終了後にも更新されます。一方、publish が共有する `run.json` はフック実行中の写しなので、その publish は `running` のままです。共有された写しだけで、送信の完了や現在のプロセスの状態を判断しないでください。

## ベンチ結果の受け取り

`bench` のフックはベンチを回し、結果を次の形で `$ISUTORI_BENCH_RESULT` に書きます。0 以外で終了したときや、結果を書かずに終了したときは、ベンチの fail ではなくエラー (終了コード 1) になります。

```json
{"passed": true, "score": 12345, "message": "ポータルに表示された内容など"}
```

`bench` には、ポータルに合わせて次のどれかを書きます。

- `isutori receive`: `http://127.0.0.1:7878/` で待ち受けます。ポータルで Enqueue し、終わったら結果をこのページのフォームに入力してください
- `isutori autobench <ポータルの URL> <対象サーバー>`: ポータルをブラウザで開き、ユーザースクリプトに Enqueue させて結果を受け取ります。待っている間も、上と同じフォームから手動で入力できます
- 自作のスクリプト: ポータルにベンチを回す API などがあれば、それを呼んで結果を書きます

`autobench` の対象サーバーは、ポータルの選択肢にある番号か IP で書きます。最後に選んだサーバーが最終計測にも使われるポータルがあるため、ユーザースクリプトは一致する選択肢が無いとき、別のサーバーで代用せず、エラーを返します。

`autobench` がブラウザを開くコマンドは `--open-command` で指定できます。未指定なら、`wslview`、`xdg-open`、`open` のうち最初に見つかったものを使います。

`receive` と `autobench` は結果をファイルに保存してから送信元へ受領の成功を返します。保存に失敗した場合はエラーを返し、再送を受け付けます。自作の bench フックも結果の保存を終えてから成功として終了してください。

### API でベンチを回す

API の利用が許可されていれば、競技リポジトリに登録・結果取得のコマンドを用意し、`hooks.bench` を差し替えられます。例えば `ops/bench-api.sh` を用意した場合は、次のように設定します。キューやほかのフックを変更する必要はありません。

```toml
[hooks]
bench = "ops/bench-api.sh"
```

導入前に、API によるベンチの登録と結果取得の可否、使える認証方法、結果を問い合わせてよい間隔を確認してください。当日マニュアルなどで分からない点は運営へ問い合わせます。許可が不明な間も、認められたブラウザ操作や手動入力で導入を進められます。

API 用コマンドは次の点を守ってください。

- 指定した対象で登録し、そのジョブの確定結果を `$ISUTORI_BENCH_RESULT` へ上記の JSON 形式で保存する。最新のジョブや途中スコアで代用しない。
- ベンチ自体が不合格でも、結果を正常に取得・保存できたら `passed: false` として終了コード 0 を返す。登録や結果取得、保存の失敗は 0 以外で終了する。
- 登録要求がタイムアウトしても、未登録とは決めつけて再送しない。既存ジョブの有無を確認し、成否が分からなければエラーとして知らせる。

資格情報は手元の認証ファイルや環境変数などから渡し、リポジトリ、ログ、エージェントへの入力に含めないでください。認証方法、ジョブの識別、結果の確定条件はポータルごとに実装します。

### ユーザースクリプト

競技リポジトリのルートで次を実行し、雛形を書き出します。URL は実際のポータルに置き換えてください。書き出したファイルを Tampermonkey に入れます。

```sh
mkdir -p ops
isutori userscript 'https://portal.example.com/*' > ops/isutori.user.js
```

当日書き換えるのは、ポータルの画面に依存する「PORTAL ADAPTER」の区間にある `adapter` だけです。書き換えるときの決まりと、ベンチを回さずに確かめる方法は、スクリプト内のコメントにあります。同梱の実装は偽ポータル向けです。書き換えたものは競技リポジトリに保存し、全員で同じものを使ってください。

まず [画面と変化を記録](#ポータルの画面と変化を記録する)し、その記録を使って adapter を書きます。[登録前の確認メニュー](#登録前の準備を確かめる)で対象選択を確かめてから、最初のベンチを実行してください。

#### ポータルの画面と変化を記録する

SPA の保存済み HTML は、JavaScript が描画した画面を含まないことがあります。また、描画後の HTML でも、選択肢の読み込み中やスコアの更新前だけを取得すると、adapter の待機条件を見誤ります。`inspect` で画面の変化を記録し、複数の状態を読み比べてください。

1. 競技リポジトリのルートで `isutori inspect https://portal.example.com/contestant` を起動する。実際のポータルの URL に置き換える。コマンドは受信口を開き、保存先と接続情報を表示する。ポータル自体は開かない。
2. 雛形の userscript を Tampermonkey に入れ、ポータルを開く。adapter はまだ書き換えなくてよい。
3. メニューの「isutori: start recording」を選び、CLI が表示した `http://127.0.0.1:7877/#...` の接続情報を貼る。画面の表示が `recording` になったことを確かめる。この接続情報をポータルの URL に付け足さない。
4. 選択欄を開き、一覧の読み込みを待ち、対象を選ぶ。完了ジョブの詳細画面も開く。記録中は同じオリジン内の画面遷移と再読み込みに対応する。別タブで記録する場合は、そのタブでも開始する。
5. 保存された履歴を読み、adapter を書く。エージェントに依頼する場合は記録の保存先を伝える。記録を続けながら「isutori: check enqueue」で準備を確かめてもよい。
6. 「isutori: stop recording」を選び、`stopped; 0 event(s) pending` を確かめてから受信コマンドを Ctrl-C で止める。保存済みのファイルは残る。

記録を始めるだけでは、対象選択やベンチ登録を行いません。実際に操作した内容はポータルへ反映されるため、登録ボタンを押す操作は通常のベンチ実行として扱います。結果の遅延更新を調べる場合は、最初のベンチ中も記録を続けられます。受信口は既存のベンチ結果用の 7878 と分け、既定では 127.0.0.1:7877 を使います。変更する場合は `--listen 127.0.0.1:ポート番号` を指定します。

保存先は、起動したディレクトリの `.isutori/inspect/<記録 ID>/` です。`events.jsonl` に時刻、受信時刻、ページ ID、ページ内の連番、取得理由、操作対象、表示状態、対応する HTML の相対パスを追記します。HTML は `snapshots/` に置き、同じ状態では前のファイルを参照します。各記録の `userscript` には、その時点の期待 ID、実行 ID、照合状態も保存します。履歴から必要な時点を選び、前後の HTML を読んでください。

DOM の変更、クリック・入力・選択変更とその処理後、タブの表示状態の変更、ページを離れる時点で取得します。1 秒ごとの取得では、属性の変更に現れない現在値も補います。input の値、チェック状態、select の選択状態、textarea の現在値は、複製した HTML に反映します。ページ自体を書き換える処理ではありません。

記録時のコード照合には既定で `ops/isutori.user.js` を使い、起動したディレクトリからの相対パスです。`--userscript FILE` で変更できます。記録ごとに作業中のファイルを読み直し、`matched`、`mismatched`、`unknown` を表示・保存します。不一致や編集中のファイルの読み取り失敗でも DOM の記録は続け、以前の一致判定は引き継ぎません。ソースを送るのはページの接続時だけで、以降はその識別子を使います。ソース照合の送信上限は JSON を含めて 1 MiB です。

記録の上限は、送信 1 件につき JSON を含めて 2 MiB、受信側は 1 回につき 100 MiB または 10,000 件です。ブラウザの送信待ちは 100 件または 8 MiB までです。上限超過や通信・保存の失敗は `STOPPED` と表示し、自動で記録を続けません。受信側の上限では、新しい inspect を起動してください。未送信分を破棄する場合は、停止の表示と保存済みの履歴を確認し、ページを再読み込みしてから新しい接続先で開始します。

通信失敗後の未送信分は、そのページを開いている間だけ保持します。同じ受信先への接続情報で「start recording」を実行すると再送を試します。応答だけを失った場合は、同じページ ID と連番で重複して記録される場合があります。未送信分を持ったまま別の受信先へ移ることは拒否します。再読み込みすると未送信分は失われるため、必要な再送を先に済ませてください。

この記録は画面を調査するための観測結果です。非表示タブのタイマーの遅れ、取得の間の短い変化、画面遷移直前の送信失敗まで完全には追えません。停止の記録が無い場合や、ページ内の連番が欠けた場合は、履歴が揃っていると判断しないでください。「変化が記録されていない」だけで、読み込み完了や結果確定とはみなしません。iframe 内、Shadow DOM 内、イベントハンドラーや Vue の内部状態は取得しません。

受信口は 127.0.0.1 に限定し、記録ごとのトークンとポータルのオリジンを確認します。Cookie、localStorage、ページ自身が保存した sessionStorage は収集しません。保存した URL からクエリとフラグメントを除き、script・style・meta と、password・hidden・file の input の値も HTML から除きます。ただし、任意の本文・属性に埋め込まれた秘密情報をすべて判別する機能ではありません。記録は手元の調査用とし、そのまま共有やコミットをしないでください。

#### adapter の準備と登録

`prepare(target)` は、対象の選択と確認を行い、選択した対象の表示名 `target` と、登録を行う `submit()` を返します。準備だけでは登録しません。選択肢の読み込みを待ち、指定した対象を選んだ後に値を読み直し、登録ボタンの操作可否を確かめてください。読み込み中の仮表示や、別のサーバーで代用しないようにします。

確認メニューと通常の実行は同じ `prepare` を使います。通常の実行だけが、その後に `submit()` を呼びます。`submit()` は対象とボタンを再確認し、登録を 1 回行ってジョブの識別情報を返します。準備結果はページ内でだけ使い、sessionStorage には保存しません。

準備中にページが再読み込みされた場合は、準備から再開します。登録を始めた後は登録し直さず、ジョブのページを確認して結果待ちに進みます。ジョブを確認できなければエラーを返すので、ポータルで成否を確認してください。

既存の adapter を移すときは、`enqueue(target)` の対象選択と確認を `prepare(target)` に移し、登録操作とジョブの識別を返り値の `submit()` に分けます。新しい雛形から作業し、直したスクリプトを Tampermonkey に入れ直してください。

#### 確定した結果だけを読み取る

`readResult(job)` は、その回に登録したジョブの確定結果だけを返します。実行中や最終結果の反映待ちは `null`、確定後は `{ passed, score, message }`、別ジョブへの移動や解釈できない状態は例外にします。`job` には再読み込み後も今回の実行を識別できる情報を保存してください。最新結果、最高スコア、前回の成功結果で代用しません。

実行中のスコアは増減し、更新が一時的に止まる場合もあります。数値の存在、一定時間の停止、キューからの消失、固定時間の経過だけでは結果確定と判断しません。今回のジョブの終了と、そのジョブの最終結果が反映されたことを確認します。成功だけでなく、確定した失敗や異常終了もベンチ結果として返します。結果を取得できなかった場合とは区別してください。

ポータルごとに、終了状態、最終結果の印、ジョブと結果の対応、必要な項目の反映順序を調べます。ソースや API の仕様を読める場合は、その意味と更新順序を確認し、`inspect` の記録で実際の表示と照らし合わせてください。終了表示とスコアが別々に更新される場合は、同じ最終結果に揃ったと判断できる根拠が必要です。揃ったと判断できなければ `null` を返し続けます。共通部分は待機期限を超えると取得エラーを報告し、途中スコアを保存しません。待機中は手動フォームへ切り替えられます。

同梱の adapter は ISUCON14 の偽ポータル向けです。URL と Summary のジョブ ID が一致し、Summary が `FINISHED`、Result が `Finished` と合否を示し、スコアが整数として読める場合に結果を返します。Summary が `ERRORED` の場合は、異常終了として `passed: false`、`score: 0` を返します。この画面は同じジョブ情報から各欄を描画します。他のポータルへ移す際は、表示名だけを置き換えず、確定条件も調べ直してください。ポータル自身が誤った結果を確定・公開する問題は、待ち時間を加えても保証できません。

adapter を書いたら、次の表示順序で確定前に結果を返さないことを自動テストで確かめます。

- 前回の確定結果が残った状態から、今回のジョブへ切り替わる
- 実行中のスコアが変化し、途中でしばらく更新が止まる
- 終了表示が先に現れ、最終結果の印、合否、スコアが後から揃う
- 成功、失敗、異常終了を取得し、別ジョブへの移動と待機期限超過は取得エラーにする

#### 登録前の準備を確かめる

1. ポータルのダッシュボードを開く。実行中や結果未報告の回があるタブでは確認できないので、別のタブを使う。
2. Tampermonkey のメニューから「isutori: check enqueue」を選び、対象サーバーの番号か IP を入力する。
3. 表示された `requested` と `selected` が意図した対象を指し、`ready: true`、`enqueued: false` になっていることを確かめる。失敗したら、表示された箇所を adapter で直して入れ直す。

この確認は対象の選択を実際に変更します。ベンチの登録、デプロイ、isutori への結果送信は行わず、ローカルの受信サーバーも不要です。画面上で準備できたことの確認なので、ポータル側が登録を受け付けるかどうかは、最初のベンチで別に確かめます。

結果の読み取りは、終わったジョブのページで「isutori: read this page」を使って確かめます。完了ジョブが無ければ、準備の確認後に最初の `isutori bench` を実行し、結果の読み取りも確認してください。

#### 実行中のスクリプトを照合する

`autobench` は自動操作の前に、ブラウザで動いているコードと競技リポジトリのファイルを照合します。既定の比較先は `ops/isutori.user.js` です。別の配置を使う場合は `--userscript FILE` で指定してください。bench フックの作業ディレクトリからの相対パスであり、その回に保存した運用コード内のファイルを使います。手元の最新の作業ツリーとは比較しません。

一致するまで `prepare`、登録、結果の読み取りへ進みません。不一致や照合不能の場合は、ブラウザに `BLOCKED`、短い期待 ID と実行 ID、理由を表示します。受信側のログにも照合情報と比較先を残します。ファイルの入れ直しを行って再読み込みするか、同じ回の手動フォームから結果を入力してください。登録開始後の再読み込みでは、照合後も登録を繰り返さず、既存のジョブを確認します。

比較先のファイルが保存済みの運用コードに無い場合や、旧形式の場合は、Tampermonkey への入れ直しだけでは直りません。その回は手動入力へ引き継げます。運用コードを直して反映した内容は、次の回から使います。

userscript は実行部分を包む `isutoriScript` 関数のソースを localhost へ送り、受信側が SHA-256 を計算します。改行コードだけを正規化し、adapter、記録処理、登録と結果読み取りのコードを照合します。空白やコメントの編集でも識別子は変わります。関数の外にある `@version`、`@match`、`@grant` や Tampermonkey の設定変更は、この識別子には含めません。送ったソースを受信側で実行したり、その全文を実行記録へ保存したりする処理はありません。

結果の `userscript` には、期待 ID の `expected`、実行 ID の `actual`、照合状態の `status` を保存します。`bench.json` と `run.json` のベンチ結果に同じ情報が入ります。自動結果は `matched`、手動フォームと `receive` の入力は `not_checked` です。手動入力をスクリプト照合済みとは扱いません。自作の bench フックは、この項目が無い従来の結果形式を使えます。古い記録に項目が無い場合も、照合済みとは判断しないでください。

旧版には新しい自動実行要求を渡さないよう、起動 URL の形式を変更しています。新しい CLI と雛形を揃えて更新し、既存の adapter は「PORTAL ADAPTER」の区間へ移してください。ラッパーの外へ処理を追加せず、版番号や識別子を手で更新する作業も不要です。照合が始まらない場合は、スクリプトが有効か、`@match` がポータルの URL と合っているか、CLI と雛形の更新が揃っているかを確認してください。原因が分からなくても、同じ回の手動フォームから結果を入力できます。

「check enqueue」と「read this page」の単独メニューは、localhost への接続やコード照合を要求しません。これらを実行できたことだけで、自動実行用のファイルとの一致を判断しないでください。

#### 報告済みの古いタブを整理する

自動整理は既定で無効です。userscript のメニュー「isutori: toggle automatic tab cleanup」で切り替えます。設定は同じ userscript 内で共有・保存され、有効にすると、すでに条件を満たす古いタブも整理します。比較用に残したいタブでは、先に「isutori: toggle keep this tab」を実行してください。この指定はタブを再読み込みしても維持します。

新しい回のタブを開いただけでは、前回の結果を閉じません。新しい回の合否・スコアを isutori が受領した後、その回より前に始めた、結果受領済みのタブを閉じます。ベンチが不合格でも、結果を受領できた回は対象です。結果取得エラーを報告できただけの回、送信失敗、実行中、照合停止のタブは残します。手動フォームで入力した回も、userscript 自身が結果の受領を確認していないため残ります。

整理対象は、autobench の起動 URL で開始し、コード照合に成功したタブだけです。Tampermonkey のタブ固有情報で管理し、手動で開いたタブや、実行状態だけをコピーした別タブは閉じません。閉じる直前にも今回のジョブ画面かを確認し、別の画面へ移っていれば残します。DOM 記録中や、未送信の記録がある場合も残します。記録を停止し、未送信分の保存が済んだ時点で条件を満たせば整理します。

グループは、同じブラウザの同じ userscript 内で、ポータルと受信先のオリジンの組ごとに分けます。オリジンにはスキーム、ホスト、ポートが含まれます。同じ組を使う競技リポジトリは同じグループになり、別の受信ポートや別のブラウザプロファイルでは共有しません。照合に成功した新しい回へ順番を付け、通知の到着時刻や実行 ID の文字列から新旧を推測しません。再読み込みで順番は更新せず、古い回の報告でも新しい回を閉じません。

タブ間の通知には Tampermonkey の保存領域を使い、終了後も localhost へ問い合わせ続ける処理はありません。`@grant window.close` を使うため、adapter の遷移を `location.replace` に変える必要はありません。閉じる操作や保存領域が使えなくても、ベンチ結果の受信は成功したままタブを残します。Tampermonkey はウィンドウの最後のタブを閉じられません。更新前から開いているタブは管理対象にならないことがあります。タブ整理は重複登録を防ぐ機能ではありません。

## うまくいかないとき

- `isutori bench` が失敗したら、その実行の `run.log` で、どのステップで何が出力されたかを確かめます。場所は、stdout に出る JSON の `run_dir` にあります
- fetch や REF の解決に失敗したときは、エラーメッセージに表示される `run.log` を開きます。この段階ではキュー登録前なので、`run.json` はまだありません
- `isutori.toml` やフックを変えたのに反映されないときは、`ops.ref` のブランチへ push したかを確かめます
- 順番が回ってこないときは、`isutori status` で先頭のチケットを確かめます。持ち主の isutori が止まっていれば、リースが切れた時点でチケットは自動で消えます
- それでもキューが詰まったままなら、チームに知らせてから `isutori queue clear` で空にします

## 偽ポータル

`isutori mock-portal` は、[ISUCON14 のポータル](https://github.com/isucon/isucon14-portal) の競技者画面を偽のデータで動かします。ユーザースクリプトを本番前に試すためのものです。

- ジョブは `--pending` と `--running` の時間をかけて進み、`--outcome` (`pass` / `fail` / `error`) の結果で終わります
- 本物と同じく、ジョブの実行中の Enqueue は 422 で断られ、対象サーバーを選ばない Enqueue は 404 になります

## 開発

### テスト

```sh
mise install
go test ./...
testenv/e2e.sh   # Docker の sshd を s1 に見立て、3 人同時の bench で排他と後始末を確かめる
```

### plugin のバージョン

skill を変えたら `plugin.json` の `version` を上げます。Codex はこのバージョンごとに plugin をキャッシュします。

### 偽ポータルの画面

偽ポータルの画面は `mockportal/` でビルドし、成果物を `internal/mockportal/dist/` にコミットしています。isutori を使うだけなら Node は不要です。

```sh
cd mockportal
pnpm install
pnpm exec playwright install chromium   # 初回のみ
pnpm build       # 画面をビルドして dist/ を更新する
pnpm typecheck   # 画面、スクリプト、ユーザースクリプトの型検査
pnpm test:unit   # ブラウザを起動せず、登録前の準備と状態の遷移を確かめる
pnpm test        # 上の検査と、偽ポータルに対するブラウザでの検査を行う
```

Dependabot が npm の依存を上げる PR では、CI がビルドし直した成果物を PR に自動でコミットします。そのコミットに対する CI は承認待ちになるので、PR の画面から承認して実行してください。
