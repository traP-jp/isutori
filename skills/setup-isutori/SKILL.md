# isutori を競技リポジトリに組み込む

この手順は導入を任されたエージェント向けである。以降の「依頼者」は導入を依頼した人を指す。

isutori が担当するのは、順番待ちのキューの管理と、順番が来たときのフックの実行だけである。デプロイ手段 (ansible、Makefile、シェルなど) や集計スクリプトの中身は作らない。フックから呼ぶものが競技リポジトリに無ければ、作業を止めて依頼者に伝える。

次の操作は、実行する前に依頼者の承認を得る。

- `git push` (フックと `isutori.toml` は origin の `ops.ref` から読まれるため、反映には push が要る)
- `isutori bench` (共有サーバーにデプロイし直し、その数分間、チームの他の人はデプロイとベンチができなくなる)

## isutori を入れる

チーム全員が同じバージョンを使うよう、競技リポジトリの mise にバージョンを固定して入れる。

```sh
mise use --pin go:github.com/traP-jp/isutori@latest
```

mise が使えない場合は、`go run github.com/traP-jp/isutori@<コミット>` を Makefile などで包み、バージョンを固定する。

入れたら、`isutori docs` で文書の一覧を見て、`isutori docs usage`、`isutori docs flow`、`isutori docs hooks` で仕様 (コマンド、測定の流れ、フックの書き方、環境変数、終了コード) を読んでから、以降の作業に進む。

## 現状を確かめる

- 競技リポジトリに `origin` があり、push できること
- `ssh s1 true` のように、各サーバーへ SSH の別名で入れること。キューを置くホスト (通常 s1) の別名を控える
- 既存のデプロイ手段と集計スクリプトを読み、それぞれをどのフック (`deploy`、`collect` など) で使うかを決める
- キューへ並ぶ前に行う処理がある場合は、`isutori docs hooks` を参照し、呼び出し元のコマンドへ組み込む

## isutori.toml を書く

`isutori init` で雛形を作り、次の点に気をつけて埋める。

- フックは、依頼者の作業ツリーではなく `ops.ref` から取り出したディレクトリで実行される。そのため、デプロイするアプリは作業ツリーから取らず、`$ISUTORI_APP_COMMIT` のコミットをサーバーへ載せる
- デプロイ手段そのものの冒頭に `isutori guard` を入れる (playbook の最初のタスク、Makefile のターゲットの 1 行目など)。`hooks.deploy` にだけ書くと、isutori を通さない直接のデプロイを止められない
- `$ISUTORI_MODE` をデプロイ手段に渡し、`final` のときはログ出力やプロファイラを切らせる
- `collect` / `analyze` の成果物は `$ISUTORI_RUN_DIR` の下に置く。publish は、そこにある結果や成果物を共有先へ送る。`isutori docs publish` の「publish フックの約束事」に従い、成果物の不足、同じ実行 ID の再送、共有処理の競合を扱う
- `cleanup` は、どのステップで失敗した後に呼ばれても動くようにする
- `hooks.bench` は、許可された API 用コマンド、`isutori autobench <ポータルの URL> <対象サーバー>`、`isutori receive` から選ぶ。autobench を使う場合はポータルの URL を確かめる
- API を使う場合は、登録と結果取得の可否、認証方法、問い合わせ間隔を当日マニュアルなどで確認し、不明点は運営へ問い合わせる。`isutori docs bench-hook` の「API でベンチを回す」に従い、競技リポジトリのコマンドを用意する。許可が不明な間は、認められたブラウザ操作や手動入力で進める
- 対象サーバーは依頼者に確かめる。最後に選んだサーバーが最終計測にも使われることがあるので、自分で推測して決めない

## ユーザースクリプトを当日のポータルに合わせる

`hooks.bench` で `isutori autobench` を使うときに行う。

### 画面を記録する

1. 当日マニュアルとポータルの注意書きに、ポータルの自動操作を禁じる記述が無いかを依頼者に確かめてもらう。禁じられていれば `hooks.bench` を `isutori receive` にし、[運用ルールの追記](#エージェント向けの運用ルールを追記する)へ進む
2. `isutori userscript 'https://portal.example.com/*' > ops/isutori.user.js` のように書き出す。実際のポータルのオリジンに置き換え、画面のパスを含めず全ページを対象にする。ポータルの URL は依頼に含まれていればそれを使い、無ければ尋ねる
3. 競技リポジトリのルートで `isutori inspect <ポータルの URL>` をバックグラウンドで起動する。`isutori docs userscript` の「ポータルの画面と変化を記録する」に従い、依頼者に雛形を Tampermonkey へ入れ、記録を開始してもらう。選択欄を開く、一覧を待つ、対象を選ぶ、完了ジョブの詳細画面を開く操作を頼む。ログイン済みのポータルを自分で操作しない。

### adapter を実装する

保存先の `events.jsonl` で操作と更新順序を調べ、必要な前後の HTML を読む。単一の状態や、変化の記録が無いことだけで読み込み完了や結果確定とは判断しない。記録の停止・欠落や未送信分も確認する。

「PORTAL ADAPTER」の区間にある `adapter` だけを書き換える。`prepare(target)` は選択と確認だけを行い、登録を行う `submit()` を返す。守るべき決まりはスクリプト内の JSDoc にある。型注釈と外側の `isutoriScript` ラッパーは保ち、ラッパーの外へ処理を追加しない。識別子の手動更新は不要である。

対象の選択にはその画面で必要なイベントだけを送る。たとえば [PrimeVue 4.5.4 の Select](https://github.com/primefaces/primevue/blob/4.5.4/packages/primevue/src/select/Select.vue#L132-L166) は `mousedown` で選択し、`click()` だけでは選べない。DOM 記録にはイベントハンドラーが含まれないため、使用バージョンのソースも確認する。選択後の表示と登録ボタンの状態を確認し、登録直前にも対象を再確認する。

合成イベントに不要な `view: window` は渡さない。Tampermonkey の実行環境では、Window のラッパーを渡してイベントの生成に失敗する場合がある。Console で動いたことだけで判断せず、雛形を入れた状態で「isutori: check enqueue」を確認してもらう。

`role="option"` だけで実際の選択肢と判断しない。PrimeVue は「No available options」などの空表示にもこの属性を付ける。仮表示を除いて候補の反映を待ち、対象の選択を確認する。空表示だけでは読み込み中・取得失敗・対象なしを区別できない。ポータルの状態とソースから調べ、判別できなければ待機期限まで待ち、何を確認できなかったかをエラーに残す。

`readResult(job)` は、今回のジョブの終了と最終結果の反映を確認してから `{ passed, score, message }` を返す。実行中や反映待ちは `null`、別ジョブへの移動や解釈できない状態は例外にする。`job` には再読み込み後も今回の実行を識別できる情報を残す。

スコアの存在や更新停止、キューからの消失だけでは確定と判断しない。終了状態と最終スコアが同じジョブの結果に揃ったと判断できる根拠を、ソースや API の仕様と DOM 記録から確認する。根拠が取れない間は待機し、前回結果で代用しない。

### 自動テストで確かめる

対応する adapter の自動テストでは、空表示の後に候補が現れる場合、操作しても選択が反映されない場合、指定対象がない場合を確認する。対象不一致や待機期限超過では登録しない。

途中スコアの変化と一時停止、前回結果の残留、終了表示より遅い最終結果の反映を再現する自動テストを用意する。成功・失敗・異常終了も確認する。別ジョブへの移動や待機期限超過を、ベンチ自体の失敗と混同しない。

### 登録前の操作を確かめる

コード照合に使うファイルは既定の `ops/isutori.user.js` とする。配置が異なれば、inspect と autobench の `--userscript` で明示する。autobench は保存済みの運用コード、inspect は作業中のファイルを比較する。依頼者に Tampermonkey へ入れてもらう。ダッシュボードで「isutori: check enqueue」を実行し、対象を明示して選択結果と操作可否を確かめてもらう。対象の選択は変わるが、登録はしないことを伝える。実行中や結果未報告の回があるタブでは確認できないので、別のタブを使ってもらう。

終わったジョブのページで「isutori: read this page」を実行してもらう。完了ジョブが無ければ、準備だけ確認し、最初のベンチで結果の読み取りも確かめる。確認メニューで分かる不具合は、ベンチを回さずに adapter を直して入れ直してもらう。

### 最初のベンチで照合を確かめる

[確かめる](#確かめる)の節で最初のベンチを回すときに、次を確認する。

ログと結果の `userscript.status` が `matched` であることを確認する。`BLOCKED` なら期待するファイルを入れ直し、同じ回のタブを再読み込みする。手動フォームへ引き継ぐ場合は `not_checked` として扱う。単独の確認メニューは照合をしないため、それだけで一致とは判断しない。

WSL から使う場合は、Windows のブラウザから `http://127.0.0.1:7878/` に届くことも確かめてもらう。ベンチ結果の受信口は `bench` のステップで開くため、その間に確認する。

### 記録を終える

記録は最初のベンチ中も続けてよい。調査が終わったら依頼者に「isutori: stop recording」を実行してもらい、未送信が 0 になってから inspect を止める。生の記録や接続トークンをコミットしない。

### 必要ならタブの自動整理を案内する

タブの自動整理は既定で無効である。依頼者が希望する場合は、残したいタブで先に「isutori: toggle keep this tab」を実行してもらう。その後「isutori: toggle automatic tab cleanup」で有効にする手順を案内する。新しい回の結果を受領した後に、古い結果受領済みタブだけを整理する。取得エラー・送信失敗・記録中・未送信の記録があるタブは残る。同じポータルと受信先のオリジンの組でグループを共有する。閉じるために adapter の遷移を変更しない。詳細は `isutori docs userscript` の「報告済みの古いタブを整理する」に従う。

## エージェント向けの運用ルールを追記する

チームの Claude Code と Codex の両方に届くよう、競技リポジトリの `AGENTS.md` に [agent-rules.md](agent-rules.md) の内容を追記する。`CLAUDE.md` には `@AGENTS.md` の行を入れて読み込ませる。既に同じ内容があれば重複させない。

## 反映する

`isutori.toml`、フック、`ops/isutori.user.js`、`AGENTS.md`、`CLAUDE.md` の変更をコミットする。依頼者の承認を得てから、`ops.ref` のブランチ (既定は main) へ push する。

## 確かめる

1. `isutori status` が通り、キューのホストに SSH で入れること
2. 依頼者の承認を得て、`isutori bench` をバックグラウンドで実行する。
3. 次の 3 点を確かめる。
   - 終了コードが 0 であること
   - `$ISUTORI_RUN_DIR` の `run.json` と `bench.json` にスコアが入っていること
   - `collect` 以降のステップの状態と出力が想定どおりであること。publish の成功は、共有先に実行 ID とベンチ結果が残ったことでも確かめる

失敗したら、`run.log` で失敗したステップを特定する。結果を取得済みで共有だけを再試行する場合は、`isutori publish <run_dir>` を使う。保存済みの publish フックが、回収や分析の成果物が無くても動き、共有サーバーを操作しないことを先に確かめる。再送で共有先へ書き込む際も、通常の共有と同じ承認条件に従う。それ以外の修正は、[反映する](#反映する)からやり直す。

共有フックは、競技サーバーを使わない検証用の保存先で、成果物が無い場合と途中までの場合、送信失敗後の再試行、成功後の再送を確かめる。同じ実行 ID の記録が増えず、失敗の履歴とベンチ結果が残ることを確認する。
